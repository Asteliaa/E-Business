# ЛР6. Ценностное предложение и цифровой товар → бизнес-модель по Канвас → бизнес-логика и сценарии → страницы и экраны → релизы

> Документ составлен по методичкам ЛР6 (архив «Лабораторные3-7.rar»). Лабораторная состоит из **5 методик**, у каждой есть Excel-шаблон. Методики идут цепочкой: результат одной становится входом для следующей.
>
> Сквозная логика ЛР6: **проблема клиента → ценностное предложение → цифровой товар → единица монетизации → Канвас → бизнес-логика → пользовательские сценарии → страницы/экраны → первый и последующие релизы**.

## 0. Цель и что сдаётся

**Что сдаётся.** В методичках нет отдельного перечня «что сдать». Каждая методика называет свой итоговый результат, а к каждой приложен Excel-шаблон. Поэтому результат работы — **5 заполненных Excel-книг** и **итоговые формы**, которые названы в методиках:

| № | Методика | Итоговый результат по методике |
|---|---|---|
| 6.1 | Ценностное предложение и цифровой товар | Паспорт ценностного предложения и цифрового товара, паспорт монетизации, карта доказательств, список гипотез |
| 6.2 | Бизнес-модель по Канвас | Заполненный Канвас, паспорт бизнес-модели, перечень гипотез, карта доказательности, список решений для проектирования |
| 6.3 | Бизнес-логика и пользовательские сценарии | Паспорт бизнес-логики, карта ролей, карта сценариев, паспорта ключевых сценариев, матрица приоритизации, контрольный лист связности |
| 6.4 | Страницы и экраны | Реестр страниц и экранов, карта навигации, матрица состояний, паспорта страниц/экранов, матрица приоритетов, контрольный лист связности |

**Общие правила оформления Excel-шаблонов.** Они повторяются в инструкциях книг:

- выпадающие списки берутся с листа «Справочники»;
- строки с пометкой «Пример, замените на реальные данные» — это образцы. Их нужно заменить данными своего проекта;
- элементы связываются через ID (P-001, VP-001, PR-001, M-001, BM-001, S-001, U-001 и т. п.), и по этим ID работают формулы INDEX/MATCH.

## 3. Методика 6.1. Ценностное предложение и цифровой товар

### 3.1. Суть
Методика задаёт последовательность перехода от отзывов, проблем клиентов и конкурентных предложений к **доказательной** формулировке ценностного предложения (ЦП), составу цифрового товара, модели выручки и проверяемым гипотезам. Центральная задача — **исключить произвольное формулирование ЦП**: его выводят из доказанной проблемы, поведения конкурентов и слабостей существующих решений.

| Блок работы | Ключевой вопрос | Итоговый результат |
|---|---|---|
| Проблема клиента | Что мешает клиенту получить нужный результат? | Формулировка проблемы, контекст, частота, значимость, доказательства |
| Конкурентные решения | Как рынок уже решает проблему? | Карта решений, стандарт рынка, зоны слабости конкурентов |
| Ценностное предложение | Какой полезный результат обещается и почему это важно? | Формула ценности, выгоды, отличия, основания доверия |
| Цифровой товар | Какая цифровая единица передаёт ценность? | Состав, уровни, сценарии, признаки качества, ограничения |
| Единица монетизации | За что клиент платит? | Платная единица, тарифная логика, границы доступа |
| Бизнес-модель | Как ценность создаётся, доставляется, удерживается и превращается в выручку? | Связка сегмента, товара, канала, отношений, ресурсов, затрат и доходов |

### 3.2. Входы и требования к доказательной базе
Источники: отзывы и оценки, сайты конкурентов, страницы тарифов, описания продуктов, FAQ и базы знаний, демонстрации и материалы продаж, профессиональные сообщества.

**Минимальная доказательная база** (требование методики):
- не менее **3 конкурентов**;
- не менее **30 релевантных отзывов** или пользовательских высказываний;
- не менее **10 страниц сайтов** с описанием товара, тарифов, функций, гарантий или сценариев.

Для узкой ниши объём может быть меньше, но у каждого вывода должно быть зафиксированное основание.

**Входные карты**, которые нужно собрать:

| Входной материал | Минимальный состав | Контроль полноты |
|---|---|---|
| Карта проблем | Проблема, сегмент, ситуация, частота, сила влияния, цитаты/ссылки | ≥ 2 независимых подтверждения или 1 сильное из профильного источника |
| Карта конкурентов | Конкурент, уровень конкуренции, товар, обещание, тариф, функции, доказательства, ограничения | ≥ 3 сопоставимых конкурента + 1 источник лучших практик |
| Карта рыночного стандарта | Функции и условия, которые есть у большинства прямых конкурентов | Отмечены распространённость и влияние отсутствия признака на доверие |
| Карта неудовлетворённости | Проблемы, которые остаются при наличии конкурентных решений | Различено: не решена / решена плохо / дорого / сложно / только для другого сегмента |
| Карта монетизации | Типы оплаты, лимиты, бесплатные зоны, платные расширения, пробный доступ | Понятно, за какую единицу ценности платят у конкурентов |

### 3.3. Ключевые понятия (что не путать)
Проблема клиента ≠ разовое недовольство. Потребительская задача ≠ название функции. ЦП ≠ рекламный лозунг или список функций. Цифровой товар ≠ вся компания или весь сайт. Единица монетизации ≠ просто цена. Носитель ценности — элемент товара, через который клиент получает пользу. Рыночный стандарт — признаки, без которых падает доверие. Конкурентное преимущество — значимо, доказано, трудно повторить, влияет на выбор.

### 3.4. Пошаговый порядок
1. **Собрать входные результаты** (раздел 4 методики):
   1. список конкурентов с уровнем конкуренции (прямой, товарно близкий, функциональный заменитель, альтернативный способ, источник лучших практик);
   2. по каждому конкуренту: обещание, функции, тарифная логика, сегменты, доказательства, ограничения, жалобы;
   3. список повторяющихся проблем из отзывов;
   4. сопоставление проблем с решениями конкурентов: решена полностью / частично / дорого / сложно / не решена / скрыта в ограничениях;
   5. признаки нормы рынка и признаки для отличия;
   6. первичный список единиц цифрового товара и способов оплаты.
2. **Сформулировать проблемное поле**: сегмент, ситуация, затруднение, последствие, текущие обходные способы, их недостаток, критерий успешного решения.
   > **Формула полной проблемы:** Проблема = сегмент + ситуация + затруднение + последствие + неудовлетворённость текущими решениями + критерий успешного результата.
3. **Приоритизировать проблемы** и выбрать опорную по индексу ИПП (см. 3.6).
4. **Сформулировать ЦП** по элементам: сегмент, опорная проблема, обещаемый результат, механизм достижения, отличие от конкурентов, доказательство, граница обещания.
5. **Проверить ЦП** по 6 критериям и индексу ИКЦП.
6. **Описать цифровой товар** по 8 слоям (см. 3.7).
7. **Определить единицу монетизации** и проверить её тремя условиями.
8. **Проверить связь товара с 9 элементами бизнес-модели.**
9. **Построить 3 уровня предложения**: базовый, расширенный, предельный.
10. **Проверить конкурентоспособность** по индексу ИКСТ.
11. **Заполнить итоговый паспорт** и минимальный набор итоговых формулировок.

### 3.5. Формулировки и шаблоны

**Рабочая (черновая) формула ЦП:**
> Для [сегмента], который в ситуации [контекст] сталкивается с [проблема], цифровой товар [название/тип] обеспечивает [измеримый результат] за счёт [механизм], в отличие от [альтернатива], потому что [доказательство и отличие].

**Пример «слабо → сильно»** (из методики): «Удобная платформа для анализа конкурентов» — слабо, потому что в формулировке нет сегмента, проблемы, результата и отличия. Сильно: «Для малых онлайн-школ без аналитического отдела сервис за один рабочий цикл собирает признаки товаров конкурентов, выделяет рыночный стандарт и показывает, какие элементы предложения стоит включить в курс и тариф».

**Формула цифрового товара:**
> Цифровой товар = полезный результат + набор цифровых функций + данные/контент + пользовательский сценарий + правила доступа + условия качества + границы использования.

**Шаблоны итоговых формулировок (Приложение 4):**

| Тип | Шаблон |
|---|---|
| Краткое ЦП | Для [сегмент] цифровой товар [название] помогает [полезный результат] без [ключевая проблема/издержка], потому что [механизм и отличие]. |
| Расширенное ЦП | Клиенты [сегмент] сталкиваются с [проблема] в ситуации [контекст]. В отличие от [альтернатива], [товар] обеспечивает [результат] за счёт [механизм], что подтверждается [доказательство]. |
| Описание товара | [Название] — это [тип цифрового товара], который включает [состав] и позволяет [сегменту] получить [результат] в сценарии [ситуация использования]. |
| Единица монетизации | Клиент платит за [единица оплаты], поскольку именно она соответствует [получаемая ценность]. Цена увеличивается при [рост объёма/пользователей/результата/уровня качества]. |
| Конкурентное отличие | Товар отличается от [конкурент/альтернатива] тем, что [отличие] приводит к [значимый результат], тогда как стандартные решения обычно [ограничение конкурентов]. |

**Минимальный набор итоговых формулировок:** одно предложение (краткое ЦП); один абзац (расширенное объяснение); паспорт цифрового товара; паспорт монетизации; карта доказательств; список гипотез (спрос, цена, состав товара, канал, удержание, конкурентное отличие).

### 3.6. Индексы и шкалы

**Индекс приоритета проблемы (ИПП)** — критерии по шкале 1–5:

> ИПП = Частота × 0,20 + Последствие × 0,25 + Неудовлетворённость × 0,20 + Платежеспособность × 0,15 + Цифровая реализуемость × 0,10 + Связь с ростом × 0,10

| ИПП | Решение |
|---|---|
| 4,50–5,00 | Брать как основу предложения |
| 4,00–4,49 | Брать как основу после уточнения сегмента |
| 3,00–3,99 | Использовать как дополнительную ценность (дополнительные модули) |
| 2,00–2,99 | Отложить, нужна дополнительная проверка |
| 1,00–1,99 | Не использовать как основу |

**Индекс качества ЦП (ИКЦП)** = (Ясность + Значимость + Отличимость + Доказуемость + Ограниченность + Монетизационная связность) / 6, шкала 1–5.
Значение ≥ 4,0 — можно формировать товар; 3,0–3,9 — нужно уточнение; < 3,0 — возврат к анализу проблемы и конкурентов.

**Проверка единицы монетизации** (все три условия обязательны):
1. клиент понимает объект оплаты;
2. объект оплаты связан с полезным результатом;
3. рост оплаты выглядит справедливым при росте ценности или использования.

Типы единиц монетизации: доступ за период, пользователь/рабочее место, пакет функций, объём использования, транзакция, результат, расширение/модуль, данные/аналитический вывод. У каждого типа методика указывает, когда он применим, и называет риск.

**Индекс конкурентной состоятельности товара (ИКСТ)**, шкала 1–5:
> ИКСТ = Стандарт × 0,20 + Отличие × 0,25 + Доказательность × 0,20 + Монетизация × 0,15 + Снижение риска × 0,10 + Защищённость × 0,10

Значение ≥ 4,0 — готовность к проверке спроса; 3,0–3,9 — уточнить состав или обещание; < 3,0 — предложение слабо отличимо.

Пороги достаточности: соответствие рыночному стандарту **не ниже 80 %** значимых признаков прямых конкурентов; **не менее 2 значимых отличий**; хотя бы 1 механизм снижения риска покупки и 1 механизм снижения риска внедрения.

### 3.10. Типовые ошибки (из методики)
- Проблему подменяют функцией («нужен личный кабинет»). Исправление: вернуться к формуле проблемы.
- Слишком широкий сегмент («бизнес», «пользователи»). Исправление: сузить по задаче, ситуации, бюджету, роли.
- Общее обещание («удобно», «эффективно»). Исправление: заменить показателем (время, риск, точность, конверсия, затраты).
- Игнорируют рыночный стандарт. Исправление: отделить обязательный минимум от зоны преимущества.
- Слабая единица монетизации (платят за доступ, хотя ценность в результатах). Исправление: сопоставить объект оплаты с пользой.
- Недоказанное отличие. Исправление: добавить сравнение, демонстрацию, расчёт.
- Завышенное обещание. Исправление: указать условия применимости.
- Товар смешивают с бизнес-моделью. Исправление: разделить товар, ЦП, канал, поддержку, выручку, затраты.

**Ограничение методики:** она не заменяет проверку спроса на реальных клиентах, экономическое моделирование, юридическую экспертизу и UX-тестирование.

## 4. Методика 6.2. Сборка бизнес-модели по Канвас на основе анализа

### 4.1. Суть
Методика задаёт порядок, в котором результаты анализа превращаются в управленческую модель из 9 блоков Канвас. **Ключевой принцип: каждый элемент бизнес-модели связан с доказательством** (сайт конкурента, отзыв, тариф, документация, кейс и т. п.), а не с общей экспертной догадкой.

- **Вход:** результаты анализа проблем, отзывов, конкурентов, цифрового товара, рыночного стандарта, тарифов, каналов и бизнес-моделей конкурентов (ЛР4–ЛР5, методика 6.1).
- **Обработка:** выводы группируются по 9 блокам, подтверждённые выводы отбираются, формулируются гипотезы, оценивается доказательность, проверяется связность.
- **Выход:** Канвас, паспорт бизнес-модели, ключевые гипотезы, список недостающих данных, решения по товару и монетизации.

### 4.2. Входы: вид анализа → блоки Канвас

| Вид анализа | В какие блоки переносится |
|---|---|
| Анализ сайтов конкурентов | ЦП, каналы, отношения, доходы, процессы, ресурсы |
| Цифровой товар по модели Левитта | ЦП, единица монетизации, ресурсы, процессы |
| Требования по модели Кано | ЦП, приоритеты товара, рыночный стандарт, дифференциация |
| Анализ отзывов | Сегменты, проблемы, ЦП, отношения, процессы поддержки |
| Классификация по уровням конкуренции | Приоритизация источников, выбор эталонов |
| Бизнес-модели конкурентов по сайтам | Все блоки, особенно доходы, каналы, процессы, партнёры, затраты |
| Рыночный стандарт | Минимальная конфигурация товара, недифференцирующие затраты |
| Конкурентные преимущества | ЦП, ресурсы, процессы, партнёры, каналы |
| Тарифы и способы оплаты | Потоки доходов, единица монетизации, товар, ЦП |

### 4.3. Пошаговый порядок (10 этапов)
1. Зафиксировать предмет бизнес-модели (тип цифрового товара и границы анализа).
2. Отобрать релевантных конкурентов: прямые — в основной контур, косвенные и альтернативные — в дополнительный.
3. Выбрать целевой клиентский сегмент.
4. Сформулировать опорную проблему (высокая частота, значимость, недостаточная закрытость конкурентами).
5. Сформулировать ЦП и отделить рыночный стандарт от дифференцирующих характеристик.
6. Описать цифровой товар по уровням: основная выгода, базовая функциональность, ожидаемые свойства, дополненные элементы, потенциальное развитие.
7. Определить единицу монетизации.
8. Заполнить 9 блоков Канвас.
9. Проверить связность.
10. Подготовить итоговый паспорт и план проверки гипотез.

> **Правило заполнения блока:** Формулировка блока = подтверждённый вывод + источник + степень уверенности + открытая гипотеза. Утверждения без указания происхождения переносить в Канвас нельзя.

Для каждого блока методика задаёт также «что выяснить», критерии и источники ответов. В шаблоне Канвас есть дополнительные ячейки «Цифровой товар как носитель ценности», «Проверка выбора клиентом» и «Потоки доходов и единица монетизации».

### 4.5. Индексы доказательности, полноты и связности

| Тип основания | Балл |
|---|---|
| Прямое доказательство (явно указано на сайте, в тарифе, документации, отзыве) | 3 |
| Косвенное доказательство (логически следует из нескольких наблюдений) | 2 |
| Повторяющийся рыночный сигнал (у нескольких прямых конкурентов / в отзывах) | 2 |
| Экспертная гипотеза | 1 |
| Нет доказательства | 0 |

- **Индекс доказательности блока** = сумма баллов утверждений блока / максимально возможная сумма × 100 %. Высокая доказательность — 75–100 %, средняя — 50–74 %, низкая — < 50 %. Блок с низкой доказательностью нельзя использовать как окончательное решение.
- **Индекс полноты** = число блоков с доказательностью ≥ 50 % / 9 × 100 %. Минимум для первичной версии — **70 %**, для стратегического решения — **не ниже 85 %**.
- **Индекс связности** = подтверждённые связи / обязательные связи × 100 %. Обязательная цепочка: сегмент → проблема → ценность → цифровой товар → единица монетизации → канал → отношения → ресурсы → процессы → затраты → доходы.

**Проверяемые связи:** сегмент ↔ проблема; проблема ↔ ЦП; ценность ↔ товар; товар ↔ монетизация; каналы ↔ сегмент; отношения ↔ сложность товара; ресурсы ↔ преимущества; процессы ↔ качество поставки; партнёры ↔ ресурсные ограничения; затраты ↔ доходы. Для каждой связи методика указывает, что делать при противоречии.

### 4.8. Типовые ошибки (заключительные положения методики)
1. Канвас заполняют как формальную анкету, а не как управленческие решения.
2. Начинают с функций цифрового товара, а не с проблемы клиента и единицы ценности.
3. Смешивают рыночный стандарт и конкурентное преимущество.
4. Указывают доходы без связи с единицей монетизации.
5. Воспринимают бизнес-модель как догму. На деле это система гипотез: чем ниже доказательность блока, тем выше приоритет его проверки.

- [ ] Определён конкретный цифровой товар, а не общая идея продукта.
- [ ] Сформулирован приоритетный клиентский сегмент.

- [ ] ЦП связано с проблемой и отличием от конкурентов.
- [ ] Разделены рыночный стандарт и конкурентные преимущества.

## 5. Методика 6.3. Бизнес-логика и пользовательские сценарии

### 5.1. Суть
Логика методики: анализ проблем + анализ конкурентов + анализ отзывов + классификация уровней конкуренции + описание цифрового товара + Канвас → **бизнес-логика** → **пользовательские сценарии**.

- **Бизнес-логика** — причинная схема: как компания находит сегмент, решает значимую проблему, доставляет ценность через цифровой товар и получает доход. **Это не пересказ Канвас.** Канвас фиксирует состав модели, а бизнес-логика объясняет причинные связи между его элементами.
- **Пользовательский сценарий** — последовательность действий, решений и реакций системы, через которую конкретный пользователь идёт от потребности к результату. Сценарий ≠ один экран, одна функция или технический процесс.

### 5.2. Входы
Анализ сайтов конкурентов, бизнес-моделей конкурентов, классификация уровней конкуренции (ЛР5); анализ отзывов; ЦП и цифровой товар (6.1); Канвас (6.2). Переносить нужно **только проверенные выводы**, которые влияют на товар, ценность, сценарии, каналы, монетизацию или операционную модель.

### 5.3. Базовая формула бизнес-логики
> Для выбранного сегмента с подтверждённой проблемой **P** компания предлагает цифровой товар **T**, который через механизм **M** даёт результат **R** лучше, быстрее, надёжнее или дешевле альтернатив **A**. Ценность доставляется через каналы **C** и сценарии **S**, доход возникает через единицу монетизации **U**, устойчивость обеспечивают ресурсы, процессы, данные и партнёрства **B**.
>
> Кратко: Сегмент → проблема → цифровой товар → механизм ценности → сценарий получения результата → монетизация → операционная способность → метрики.

### 5.4. Пошаговый порядок (10 шагов)

| Шаг | Действие | Контрольный вопрос |
|---|---|---|
| 1 | Собрать выводы всех анализов в единый банк | На чём основан каждый вывод? |
| 2 | Выбрать целевой сегмент и опорную проблему | Проблема частая, значимая и решаемая? |
| 3 | Сформулировать механизм создания ценности | Почему товар реально уменьшает проблему? |
| 4 | Определить цифровой товар как носитель ценности | Что именно продаётся и используется? |
| 5 | Связать товар с единицей монетизации | Следует ли оплата из получаемой ценности? |
| 6 | Собрать бизнес-логику в цельную формулировку | Связаны ли элементы причинно, а не просто перечислены? |
| 7 | Определить пользовательские роли | Кто использует, платит, влияет, администрирует? |
| 8 | Сформировать семейства сценариев | Какие сценарии обязательны для создания, доставки и монетизации? |
| 9 | Описать ключевые сценарии в паспортах | Связан ли сценарий с проблемой, ценностью, товаром и блоком Канвас? |
| 10 | Проверить связность и приоритетность | Что обязательно для первой версии, а что можно отложить? |

**Этап 1. Карточка аналитического вывода:** источник → факт (без оценки) → интерпретация → вывод для бизнес-логики → вывод для сценариев → доказательность.
Шкала доказательности: **высокая** (несколько независимых источников, прямые конкуренты, повторяющиеся отзывы) — можно использовать в ключевых решениях; **средняя** — использовать как гипотезу; **низкая** (единичное наблюдение) — без дополнительной проверки не использовать.

**Этап 2. Критерии выбора проблемы:** частотность, значимость, платёжная готовность, решаемость цифровым товаром, дифференциация.
> Шаблон опорной проблемы: У [целевой сегмент] возникает проблема [содержание] в ситуации [контекст], потому что [причина]. Это приводит к [потери или ограничения]. Существующие решения неудобны или недостаточны, так как [пробел конкурентов или заменителей].

**Этап 3. Состав бизнес-логики:** сегмент, проблема, ценность, цифровой товар, механизм получения ценности, монетизация, каналы, операционная способность, метрики.
> Развёрнутый шаблон: Мы работаем с [сегмент], который сталкивается с [опорная проблема] в ситуации [контекст]. Для решения предлагается [цифровой товар], который обеспечивает [измеримый результат] за счёт [механизм ценности]. Пользователь получает ценность через сценарии [ключевые сценарии], а компания монетизирует её через [единица монетизации]. Устойчивость обеспечивается [ресурсы, процессы, данные, партнёрства], результат проверяется метриками [метрики].

Бизнес-логику записывают **в трёх версиях**:

| Версия | Объём | Требования |
|---|---|---|
| Полная | 1 абзац, 7–10 строк | Сегмент, проблема, товар, ценность, сценарий, монетизация, ресурсы, метрики |
| Краткая | 1 предложение | Сохранить связь «проблема → способ получения дохода» |
| Проверочная | Структурная запись по цепочке | У каждого элемента есть источник и доказательность |

**Этап 4. Роли:** конечный пользователь, покупатель, лицо, принимающее решение, лицо, влияющее на выбор, администратор, партнёр.
> Контроль роли: вместо «пользователь регистрируется» пишем «конечный пользователь регистрируется для получения первого результата», «покупатель оплачивает пакет», «администратор выдаёт доступы команде».

**Этап 5. Классы сценариев (9):** обнаружение проблемы; сравнение и доверие; вход и активация; основные сценарии получения ценности; монетизация; удержание; поддержка и восстановление; административные; партнёрские. Для каждого класса методика указывает связь с блоками Канвас.

**Этап 6. Паспорт сценария (поля):** название (в форме действия), роль, контекст, триггер, цель пользователя, проблема или барьер, предусловия, основные шаги, данные, результат, точка монетизации, метрики, риски, связь с Канвас.
> Краткое описание: Когда [роль] находится в ситуации [контекст] и сталкивается с [проблема или барьер], он хочет [цель]. Цифровой товар помогает ему [механизм действия] и приводит к [результат]. Для компании сценарий важен, потому что поддерживает [блоки бизнес-модели] и влияет на [метрики].

**Детализация шагов:** № шага | действие пользователя | действие системы | ценность шага | данные | риск | метрика. Типовой путь из методики: точка входа → выбор цели/ввод данных → предварительный результат → уточнение, сохранение, сравнение → ограничение бесплатного доступа → оплата, продление, расширение.

**Этап 7. Проверка связности сценария:** проблема → сценарий; сценарий → ценность; ценность → товар; сценарий → монетизация; сценарий → канал; сценарий → ресурсы; сценарий → метрика; сценарий → конкурентное отличие.
> Минимальная проверочная запись: Сценарий S нужен, потому что решает проблему P у сегмента G; ценность V создаётся через элемент товара T; пользователь получает результат R; компания получает эффект E через монетизацию U или метрику M; реализация требует ресурсов B; конкурентное отличие D подтверждено анализом.

**Этап 8. Индекс приоритета сценария** (критерии 1–5):
> Индекс = ценность × 0,25 + монетизация × 0,20 + частота × 0,15 + риск отказа × 0,15 + конкурентное значение × 0,10 + доказательность × 0,15 − сложность × 0,10

Высокий индекс при высокой доказательности — ядро первой версии. Высокий потенциал при низкой доказательности — сценарий нужно проверить. Высокая сложность при слабой связи с ценностью — перенос в последующие версии.

**Этап 9. Итоговый комплект:** паспорт бизнес-логики, карта ролей, карта сценариев, паспорта ключевых сценариев, матрица приоритизации, контрольный лист связности.
> Финальная формулировка: Цифровой товар [название] предназначен для [сегмент], который сталкивается с [опорная проблема]. Товар создаёт ценность за счёт [механизм] и позволяет получить [измеримый результат] через сценарии [ключевые сценарии]. В отличие от [конкуренты/заменители], товар обеспечивает [отличие]. Монетизация строится на [единица монетизации], потому что пользователь платит за [основание ценности]. Модель поддерживается [ресурсы, процессы, данные, партнёрства] и проверяется через [метрики].

### 5.5. Шаблоны таблиц методики

> **Расхождение методики и шаблона.** Индекс приоритета сценария в docx — взвешенная сумма из 7 критериев. В Excel это произведение четырёх оценок / 20. Укажите, какой расчёт используете.

### 5.7. Типовые ошибки (п. 14.4)
Начинают с функций, а не с проблемы. Смешивают пользователя и покупателя. Монетизация не связана с ценностью. У сценария нет метрики. Сценарии не покрывают весь путь (есть только основной функциональный). Нет связи с конкурентным анализом и рыночным стандартом. Слишком общие формулировки («удобный сервис»). Не учтены операционные ограничения (данные, поддержка, интеграции).

### 5.8. Контрольный лист готовности (п. 14.3)
- [ ] Выбран целевой сегмент, описанный не слишком широко.
- [ ] Опорная проблема подтверждена отзывами или конкурентным анализом.
- [ ] Проблема связана с платёжной готовностью или экономическим смыслом.
- [ ] ЦП сформулировано как результат, а не как перечень функций.
- [ ] Цифровой товар описан как единица предоставляемой ценности.
- [ ] Единица монетизации связана с результатом, доступом, периодом, объёмом или уровнем сервиса.
- [ ] Бизнес-логика показывает причинную связь «проблема → товар → ценность → доход».
- [ ] Роли разделены: пользователь, покупатель, администратор, лицо влияния.
- [ ] Есть сценарий получения первой ценности.
- [ ] Есть сценарий регулярного получения ценности.
- [ ] Есть сценарий оплаты, продления или расширения доступа.
- [ ] Есть сценарии поддержки и восстановления после ошибки.
- [ ] Каждый ключевой сценарий связан хотя бы с одним блоком Канвас.
- [ ] Для каждого ключевого сценария определена метрика успеха.
- [ ] Сценарии приоритизированы по ценности, монетизации, риску и доказательности.

Качественный результат отвечает на **4 вопроса**: почему товар нужен пользователю; почему пользователь выберет именно его; за что возникает оплата; какие сценарии реализовать в первую очередь.

## 6. Методика 6.4. Переход к страницам сайта и экранам приложения

### 6.1. Суть
Методика определяет, какие страницы, экраны, состояния и переходы нужны для реализации бизнес-логики цифрового товара. Страница или экран — **функциональная единица товара**: она обслуживает пользовательскую задачу, реализует часть ЦП, поддерживает монетизацию или операционную устойчивость.

> **Главный принцип:** страница или экран не создаются потому, что «так принято у конкурентов». Для их появления нужны подтверждённая пользовательская задача, бизнес-функция, информационный объект, действие или состояние взаимодействия.

### 6.2. Входы
Анализ проблем и отзывов; анализ конкурентов по сайтам (рыночный стандарт страниц); модели Левитта и Кано (обязательные, усиливающие и экспериментальные экраны); классификация конкурентов (обязательные решения берут у прямых конкурентов, вдохновение — у эталонных); ЦП; цифровой товар и единица монетизации; Канвас; пользовательские сценарии (6.3).

**Требования к исходным выводам:** у каждого есть источник; факт отделён от интерпретации; указан уровень доказательности (высокий/средний/низкий); спорные выводы не служат основанием для обязательных экранов (они идут в гипотезы); вывод, подтверждённый несколькими анализами, получает повышенный приоритет.

### 6.3. Базовые единицы проектирования
Страница сайта, экран приложения, состояние, интерфейсный блок, действие пользователя, переход, информационный объект, целевое действие. Их нельзя смешивать.

### 6.4. Логика перехода и индекс необходимости
Проблема → ценность → товар → монетизация → сценарий → страница/экран → показатель. К каждой единице задаются 4 вопроса: какую проблему решает, какое обещание ценности подтверждает, какую бизнес-функцию поддерживает, какой сценарный шаг обеспечивает.

> **Индекс необходимости** = (значимость задачи × доказательность проблемы × влияние на ценность × влияние на монетизацию × частота использования) / сложность реализации. Каждый множитель — 1–5.
> Если влияние на ценность или монетизацию = 1, экран нужно дополнительно проверить: он может быть вспомогательным или избыточным.

### 6.5. Пошаговый порядок (10 этапов)
1. **Сбор и нормализация выводов** в «банк проектных выводов»: код (P-01, C-04, BM-07, SC-03), источник, факт, интерпретация, проектное следствие, доказательность, приоритет (обязательный / важный / дополнительный / гипотеза).
2. **Роли, задачи, контексты.** Для каждой роли: цель, контекст (когда, где, с какого устройства), задачи, барьеры, нужные страницы/экраны, критический показатель. Правила: роль выделяют по задачам и правам, а не по должности. Если пользователи видят одни экраны, но принимают разные решения, это разные роли. Для приложения фиксируют контексты (быстрый доступ, уведомление, слабая связь), для сайта — поиск, сравнение, доверие, заявку, оплату, возврат.
3. **Сценарии → карта взаимодействия.** 8 сценарных шагов: вход в сценарий → понимание ценности → проверка соответствия → принятие решения → первое получение ценности → регулярное использование → поддержка и ошибки → продление и развитие. К каждому шагу 7 вопросов: задача; страница/экран; данные; доступные действия; системное событие; ошибки и исключения; показатель.
4. **Информационные объекты и действия** (пользователь, подписка, цифровой результат, заказ/заявка, обучающий модуль, уведомление) с их действиями и состояниями. Правило: объект с несколькими значимыми состояниями или действиями получает отдельную страницу, экран, раздел или карточку. Вспомогательный объект становится блоком внутри другой страницы. Для объекта, связанного с оплатой, правами или юридически значимым действием, обязательно описывают состояния ошибки, подтверждения и истории.
5. **Состав страниц сайта:** главная; страница проблемы/сценария; страница цифрового товара; тарифы; сравнение; доказательства; регистрация/заявка; оплата; личный кабинет; помощь и вопросы; правовые документы. У каждой страницы есть источник обоснования.
   Критерии включения страницы: поддерживает отдельную задачу или этап решения; нужна для ценности, доверия, оплаты, доступа или поддержки; закрывает повторяющийся барьер; имеет собственный показатель; не дублирует другую страницу.
6. **Состав экранов приложения:** стартовый, вход/регистрация, первичная настройка, главная рабочая область, выполнение основной задачи, результат, история, уведомления, профиль и настройки, поддержка.
   Специфика приложения: одна основная задача на экран; частые действия быстрее редких настроек; состояния понятны без длинного текста; уведомления — часть сценария; для оплаты и доверия нужны объяснение, подтверждение и отмена; отдельные состояния для слабого соединения и отсутствия данных.
7. **Навигация и переходы.** Типы переходов: сценарный, возвратный, сервисный, коммерческий, по состоянию, персонализированный. Для каждого указано, что проверить. Матрица навигационной связности: узел | назначение | куда ведёт | состояния | критерий качества.
8. **Состояния.** Начальное, пустое, загрузка, ошибка, успех, ограниченный доступ, предупреждение, повторное использование. Ошибку описывают как состояние сценария, по 5 вопросам: что произошло; почему это важно; что можно сделать; что система сохранит; куда обратиться.
9. **Приоритизация.** Уровни: **обязательные** (без них нельзя понять, купить, использовать); **важные** (сравнение, доказательства, история, настройки, FAQ); **развивающие** (рекомендации, персонализация, приглашения); **гипотезы**. Критерии 1–5: значимость задачи, доказательность, влияние на ценность, влияние на монетизацию, частота, сложность.
   > Минимальный состав первой версии обеспечивает цепочку «обнаружение ценности → доверие → выбор → оплата или заявка → первое получение результата → базовая поддержка».
10. **Паспорт страницы/экрана:** название, тип, роль, сценарный шаг, проблема и ценность, основная задача, основное действие, входные данные, выходные данные, состояния, переходы, требования к содержанию, показатель эффективности, источник обоснования.
    Пример из методики — «Страница выбора тарифа»: роль — потенциальный покупатель; проблема — непонятно, какой вариант подходит под задачу и бюджет; ценность — прозрачный выбор без переплаты; действие — выбрать тариф и перейти к оплате; состояния — новый пользователь, тариф выбран, ошибка оплаты, активная подписка, истёкший доступ; показатель — доля переходов в оплату и доля отказов.

### 6.6. Проверка полноты, связности, коммерческой обоснованности

| Проверка | Норма | Сигнал проблемы |

| Ценность | Каждый ключевой экран связан с проблемой и ЦП | Экран не связан с результатом пользователя |

## 7. Методика 6.5. Деление разработки на первый и последующие релизы

### 7.1. Суть
Методика определяет, что входит в **первый рыночный выпуск**, а что переносится в последующие релизы без разрушения ценностного предложения. Управленческая задача — быстро и экономно выйти на рынок, сохранить ядро ценности, заложить удержание и основу роста.

> **Ключевой принцип:** первый релиз не должен быть максимально полным. Он должен быть **минимально достаточным**: подтвердить ЦП, запустить монетизацию, собрать данные поведения и дать основание для повторного использования.

Цепочка: проблема клиента → ЦП → цифровой товар → сценарий → интерфейсная единица → монетизация → удержание → рост аудитории.

### 7.2. Входы (единый банк выводов)
Проблемы пользователей (карточка проблемы с баллами); рыночный стандарт (матрица конкурентов, ЛР5); конкурентные преимущества; ЦП и цифровой товар (6.1); Канвас (6.2); бизнес-логика — роли, правила, статусы (6.3); сценарии (6.3); страницы и экраны (6.4). Для каждого вида анализа методика формулирует вопрос, на который он отвечает при делении на релизы.

### 7.3. Термины
Релиз (состав, аудитория, метрики, ограничения, дата, критерии успеха); первый рыночный выпуск (**не черновой прототип**: нужны работоспособная ценность, базовое доверие, измерение поведения); последующий релиз; ядро ценности; единица монетизации; сценарий удержания; сценарий роста; отложенная возможность.

### 7.4. Пошаговый алгоритм (10 шагов)
1. Собрать единый банк выводов.
2. Выделить ядро ЦП, то есть результат, который пользователь получит уже в первом выпуске.
3. Определить целевой сегмент первого выпуска и исключить второстепенные.
4. Выделить единицу цифрового товара и единицу монетизации.
5. Построить минимальную цепочку: привлечение → понимание ценности → регистрация/заявка → получение результата → оплата или иной целевой обмен → повторное использование.
6. Составить полный перечень функций, страниц, экранов, данных, интеграций и сервисных операций.
7. Оценить каждый элемент по ценности, доказательности, сценарной необходимости, монетизации, удержанию, росту, сложности и риску.
8. Назначить элементы в первый релиз или последующие, либо исключить.
9. Проверить, что первый релиз не разрушает ЦП, доверие, базовую монетизацию и измерение поведения.
10. Сформировать карту релизов: цель, состав, метрики, условия перехода.

**«Сжатия» первого релиза:** сегмент → проблема → сценарий → функция → интерфейс → операция (где допустима ручная работа) → рост (события аналитики, обратная связь).

### 7.5. Что можно и что нельзя сокращать
Сокращают: число сегментов, сценариев, функций, экранов, интеграций, тарифов, глубину автоматизации, визуальную сложность. Сохраняют: главный сегмент, критический сценарий, надёжность результата, понятность и доверие, один проверяемый способ монетизации.

> **Граница экономии:** нельзя экономить на доверии, завершённости ключевого сценария, понимании результата, безопасности оплаты, фиксации действий пользователя и возможности получить обратную связь.

### 7.6. Критерии включения в первый релиз
Связь с ЦП; связь с ключевой проблемой; сценарная необходимость; монетизация; рыночный стандарт; доверие и снижение риска; удержание (минимальная версия); рост аудитории (чаще переносится); данные и аналитика (события и обратная связь **включаются обязательно**); законодательные и организационные требования (включаются без обсуждения).

### 7.7. Балльная модель: индекс релизного приоритета (ИРП)
Показатели по шкале **0–5**: ЗП — значимость проблемы, СЦ — связь с ЦП, СС — сценарная центральность, МН — монетизация, УД — удержание, РА — рост аудитории, ДК — доказательность, СЛ — сложность, РЗ — риск.

> **ИРП** = (0,20·ЗП + 0,20·СЦ + 0,15·СС + 0,15·МН + 0,10·УД + 0,10·РА + 0,10·ДК) − (0,15·СЛ + 0,10·РЗ)

| ИРП | Решение | Действие |
|---|---|---|
| ≥ 3,5 | Первый релиз | Включить или найти простейшую реализацию |
| 2,5–3,49 | Кандидат в релиз 1 или 2 | Проверить разрыв сценария; при высокой сложности упростить |
| 1,5–2,49 | Последующий релиз | Оставить в карте развития |
| < 1,5 | Не включать в ближайший цикл | Гипотеза или исключение |

### 7.8. Последующие релизы (у каждого своя бизнес-цель)

| Релиз | Цель | Типичный состав | Условие запуска |
|---|---|---|---|
| 0 — подготовительный | Данные, прототип, тексты, правила, аналитика | Прототип, карта сценариев, контент, правовые тексты, события аналитики, ручные процедуры | До или параллельно с релизом 1 |
| 1 — первый рыночный | Проверить ЦП и готовность к целевому действию | Витрина, описание товара, регистрация/заявка, ключевой сценарий, базовая оплата/заявка, профиль, поддержка, аналитика | Минимальная завершённость ядра ценности |
| 2 — удержание и качество | Повторное использование, снижение отказов | Onboarding, уведомления, история, прогресс, поддержка, состояния ошибок, база знаний | После данных релиза 1 |
| 3 — рост аудитории | Привлечение, масштаб каналов | Реферальные механики, публичные страницы, контент, партнёрские сценарии, SEO, социальные доказательства | После подтверждения ценности и удержания |
| 4 — расширение продукта | Глубина ценности, средний доход, сегменты | Новые роли, тарифы, аналитика, автоматизация, модули, интеграции | После понимания экономики |
| 5 — масштабирование | Снижение операционных затрат, надёжность | Автоматизация процессов, администрирование, производительность, безопасность, отчётность | При повторяемой нагрузке и росте |

Для каждого этапа пути (осознание → сравнение и доверие → регистрация → первая ценность → оплата → поддержка → повторное использование → рост) методика указывает минимум для релиза 1 и то, что обычно переносится. Минимальный механизм удержания задан для 6 типов продуктов (периодическая задача, образовательный товар, SaaS, маркетплейс, контентный, финансовый). Для механизмов роста (SEO, рекомендации, социальные доказательства, партнёры, сетевой эффект, платное привлечение) указано, нужен ли механизм в релизе 1.

### 7.9. Проверка сохранения ЦП (6 вопросов)
Понятно ли, какую проблему решает продукт? Может ли пользователь пройти основной сценарий до результата? Есть ли цифровой товар как предмет обмена? Есть ли основание для доверия? Есть ли целевое действие? Есть ли способ измерить реакцию рынка?

> **Критерий готовности первого релиза:** пользователь понимает обещание, выполняет ключевое действие и получает минимально достаточный результат, а команда может измерить поведение и принять решение о следующем релизе.

**Пять условий корректного первого релиза:** сохраняет ядро ЦП; позволяет пройти основной сценарий; содержит единицу товара и монетизации; включает минимум доверия и аналитики; оставляет траекторию удержания и роста.

### 7.10. Релизная карта и протокол
**Поля релизной карты:** цель релиза, целевой сегмент, проблема, ценность, состав, исключения, метрики, решение после релиза.

**Шаблон карты релизов:** релиз | цель | состав | метрики успеха | основание перехода (заполнен пример для релизов 1–4).

**Паспорт функции/страницы/экрана:** название, тип, связанная проблема, связанное ЦП, связанный сценарий, степень необходимости (обязателен / желателен / дополнительный / экспериментальный), ИРП, решение по релизу (1, 2, 3, 4, исключить, уточнить), доказательства.

**Матрица спорных элементов:** элемент полезен, но дорог → упрощённая или ручная реализация, иначе перенос; элемент есть у всех прямых конкурентов → проверить, стандарт ли это; элемент нужен для роста → в релиз роста; элемент нужен для доверия до оплаты → включить в базовой форме; элемент нужен только команде → временно ручная процедура; элемент нравится команде, но не подтверждён → оставить гипотезой.

**Итоговый протокол утверждения первого релиза:** решение (утверждён / требует сокращения / требует расширения / не готов); состав; главные исключения и причины; критические риски; метрики запуска; порог продолжения; порог пересмотра; ответственные.

### 7.12. Типовые ошибки (п. 15)
Первый релиз определяют по принципу «что успеем». Из релиза 1 удаляют монетизацию. Удаляют аналитику поведения. Пытаются обслужить все сегменты. Копируют конкурентов без понимания причины. Считают все отложенные функции одинаково важными. Запускают продукт без повода вернуться.

**Итоговые принципы:** сначала ценность, затем функции; сначала сценарий, затем экран; сначала проверка, затем масштабирование; сначала простая реализация, затем автоматизация; сначала доказательства, затем расширение.
